What It Does

This is a customer propensity model that predicts the likelihood of a Breadfast customer converting into a new vertical — food (restaurants), beauty, or shops — within 14 days of a given anchor date.

The target population is customers who are active on Breadfast (placed orders recently) but have never ordered in the target vertical. The model assigns each of them a propensity score between 0 and 1, which can then be used to prioritize who to target with campaigns or coupons.

Conversion definition: A customer "converts" if they place at least one delivered order in the target vertical within 14 days after the anchor date.

The pipeline runs in three sequential stages:

→
Stage 2
Model

Trains or loads a logistic regression. Writes propensity scores to BQ.

Stage 3
Evaluation

Computes accuracy, AUC, capture rate. Appends a row to model_results.

Stage 1 — Data Loading (core/render.py)

For a given use_case + anchor_date combination:

  1. Checks if a BigQuery table {BQ_DATASET}.{use_case}_{anchor_date} already exists.
  2. Cache hit: reads and returns the cached table directly — no SQL re-run.
  3. Cache miss: selects the right Jinja2 SQL template (tries {use_case}_query first, falls back to query), renders it with the anchor date and use-case filter, then runs it as a BigQuery QueryJobConfig with a destination table. Results are written directly in BQ — no data passes through Python during the write. The table is then read back into a DataFrame.
Re-running the same date: The second run is instant — it hits the cached BQ table and skips the SQL query entirely.

Stage 2 — Model (models/logistic_regression.py)

Three callable functions depending on the mode:

  • train() — fits a new model and saves it to models/{use_case}_logistic.pkl.
  • score() — loads a saved model and scores all customers without re-training.
  • analyze() — loads a saved model and computes feature coefficients and permutation importance.

Stage 3 — Evaluation (core/accuracy.py)

Only runs in train mode. Computes all metrics on the held-out test set (30% of data) and appends one row to model_results in BigQuery.

SQL Templates

Generic template (templates/query) — beauty & shops

Built in 5 CTEs:

  1. never_ordered_before — identifies customers with 0 vertical orders AND ≥1 order in the last 90 days.
  2. ordered_after — identifies customers who placed a vertical order in the 14-day conversion window after anchor_date. This becomes the converted label.
  3. order_agg — aggregates order-level metrics (order value, basket size) per customer from the 90-day lookback.
  4. customer_events_data — counts vertical product views and unique products viewed from app events in the 90-day lookback.
  5. customer_search_results — computes ratio of search sessions that led to a vertical PDP in the 90-day lookback.

Food template (templates/food_query)

Built in 7 CTEs with a shorter 30-day lookback and food-specific features:

  1. customer_fp_count — counts orders per fulfillment point per customer in the last 30 days.
  2. customer_primary_fp — identifies the FP a customer orders from most (used for filtering to New Cairo).
  3. events_data — counts how many times a customer opened the Restaurants vertical in the app in the last 30 days.
  4. never_ordered_before — identifies customers with 0 restaurant orders ever AND ≥1 order in the last 30 days. Also computes the vertical_orders_after conversion signal here.
  5. base / order_level — product and order level rows for the 30-day lookback window.
  6. coupon_sent — identifies customers who received a restaurant coupon in the last 30 days (joined but not currently used as a feature).
  7. agg_averages + product_averages — final per-customer aggregations of all features.
Important — no future leakage: All features are computed exclusively from orders within the lookback window (before anchor_date). The converted label is based on orders after anchor_date and is always excluded from the model's feature matrix via DROP_COLS.

Model Architecture

A single sklearn Pipeline with three steps:

StepComponentPurpose
1 SimpleImputer(strategy="median") Fills missing values with the median of each feature. Handles customers with sparse order history.
2 StandardScaler() Normalizes all features to zero mean and unit variance so regularization treats them equally.
3 LogisticRegression(max_iter=1000, class_weight="balanced") Linear classifier. class_weight="balanced" compensates for the low conversion rate (~1–5%) by upweighting positive examples.

Train/test split: 70% train, 30% test, random_state=42.

Saved model path: models/{use_case}_logistic.pkl (one file per use case).

Note on accuracy: With conversion rates of 1–5%, accuracy of 95–99% is trivially achieved by predicting everyone as non-converter. Rely on AUC and capture_rate_at_10pct as the primary quality signals, not raw accuracy.

Evaluation Metrics

MetricWhat It MeansGood Range
auc Area under the ROC curve. How well the model ranks converters above non-converters. > 0.70
capture_rate_at_10pct Of all customers who actually converted, what % were in the model's top 10% by score? This is the primary business metric — the higher, the fewer people you need to target to catch most converters. > 40–50%
precision_at_k Of the top 10% by score, what % actually converted? Higher than baseline
baseline_conversion_rate % of customers in the test set who converted. Use this to benchmark accuracy and precision. Reference only
accuracy % of predictions correct at 0.5 threshold. Misleading with imbalanced classes — do not use as the primary metric. Ignore
precision / recall At the 0.5 probability threshold. The threshold is not calibrated for imbalanced data, so these numbers are also unreliable at face value. Context-dependent

Run Commands

Train a new model

python -m core.propensity --use-case food --anchor-date 2026-03-01 --mode train
python -m core.propensity --use-case beauty --anchor-date 2026-03-01 --mode train
python -m core.propensity --use-case shops --anchor-date 2026-03-01 --mode train

Score customers with a saved model (no re-training)

python -m core.propensity --use-case food --anchor-date 2026-06-22 --mode score

Analyze feature importance

python -m core.propensity --use-case food --anchor-date 2026-03-01 --mode analyze
anchor-date: Use a historical date (at least 14 days in the past) so the conversion window has elapsed and the converted labels are complete. Running with today's date will produce all-zero labels since no one can have "converted" yet.

Configuration

All configuration lives in configs/lookup.py.

VariableValuePurpose
BQ_PROJECT bf-data-dev-qz06 GCP project for all BQ reads and writes.
BQ_DATASET test_dinayasser BQ dataset where all output tables are written.
FOOD_FPS 7 New Cairo FP names Fulfillment points used to restrict the food model's population. Automatically applied when use_case="food".
DROP_COLS ["customer_id", "converted", "unique_views_in_cat", "primary_fp"] Columns always excluded from the feature matrix. converted is the label; the rest are IDs or deprecated columns.
VERTICAL_LOOKUP dict of use_case → SQL fragment Injected into SQL templates as {{use_case_filter}} to define what counts as a vertical order.
FEATURES dict of use_case → list or None Per-use-case feature allowlist. Defined but not currently applied in model code — the model uses all non-dropped columns.
